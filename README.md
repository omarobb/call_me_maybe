# call me maybe

## Description

**call me maybe** is a function-calling tool that turns a natural-language request into a
structured, schema-compliant function call — without ever asking the LLM to "just output
JSON and hope." Given a prompt like:

```
"What is the sum of 265 and 345?"
```

the program does not answer `610`. Instead it produces:

```json
{
  "prompt": "What is the sum of 265 and 345?",
  "name": "fn_add_numbers",
  "parameters": { "a": 265, "b": 345 }
}
```

The function name and every argument value are picked by **Qwen/Qwen3-0.6B**, a 0.6B-parameter
model, guided token-by-token by a custom **constrained decoder**. The decoder masks the model's
logits at every generation step so that only tokens which keep the output both syntactically
valid JSON *and* compliant with the function's schema are ever allowed to be chosen — guaranteeing
100% parseable output even though the same model, prompted normally, would produce broken JSON
a large fraction of the time.

If none of the available functions genuinely match the request, the model can fall back to a
built-in `unknown` function rather than being forced into picking the wrong tool.

## Instructions

### Requirements

- Python ≥ 3.14
- [`uv`](https://docs.astral.sh/uv/) for dependency management
- The `llm_sdk` package (included in this repository under `llm_sdk/`)

### Installation

```bash
make install
```

This installs `uv` if needed and runs `uv sync`, which creates the virtual environment and
installs all dependencies (`pydantic`, `flake8`, `mypy`, `accelerate`, `llm_sdk`, ...) as pinned
in `uv.lock`.

### Running

```bash
make run
```

which is equivalent to:

```bash
uv run python -m src \
  --functions_definition data/input/functions_definition.json \
  --input data/input/function_calling_tests.json \
  --output data/output/function_calling_results.json
```

All three flags are optional — by default the program reads from `data/input/` and writes to
`data/output/function_calling_results.json`.

## Algorithm Explanation

The constrained decoder works as a small state machine (`GenState`) with four states:
`IN_FUNCTION_NAME`, `IN_PARAMETER_VALUE_STRING`, `IN_PARAMETER_VALUE_NUMBER`, and
`IN_PARAMETER_VALUE_FLOAT`. Generation proceeds in three phases per prompt:

1. **Function name selection** — the model generates tokens for `{"name": "`, but at every step
   `mask_logits` sets the logit of any token that would *not* keep the in-progress string a valid
   prefix of one of the known function names to `-inf`. This means the model can only ever
   complete a name that actually exists in `functions_definition.json` (plus the fallback
   `Unknown` function) — it can never hallucinate a function.

2. **Parameter value generation** — once a function is selected, its schema (`parameters` dict)
   is walked in order. For each parameter, the appropriate state is chosen based on its declared
   type (`string`, `integer`, `number`), and a matching validity check
   (`is_valid_string_continuation`, `is_valid_integer_continuation`,
   `is_valid_number_continuation`) masks every token that would break either JSON string/number
   syntax or the field's type at each step.

3. **Assembly** — the `{`, `}`, `,`, and key labels around each value are inserted directly by
   the code (not generated by the model), so the model is only ever responsible for the parts
   that actually require language understanding: which function fits, and what the parameter
   values are.

Two extra safeguards sit on top of the pure grammar mask:

- **Numeric-literal grounding**: every integer/decimal literal actually present in the user's
  prompt is pre-extracted with a regex. While generating a number field, once the digits typed
  so far match one of those literals exactly, the next token is forced to `,`/`}` (or `.` for a
  float that should continue into its decimal part), so the model can't run past the correct
  value into the next field.
- **Repetition guard**: while generating a string field, if the last N characters repeat the N
  characters before them (checked for several block sizes), generation is cut off and the string
  is closed immediately — this stops the small model's tendency to loop on a value once it drifts
  off the source text.

## Design Decisions

- **Grammar-first, prompt-second.** The instruction text given to the model exists only to bias
  *which* function and *which* substrings it reaches for — it is not relied on for output
  validity. Every character that ends up in the final JSON is either directly inserted by code
  (structural tokens) or passed through the logit mask (content tokens), so a weak or ignored
  instruction can degrade accuracy but can never produce invalid JSON.
- **Type-specific masks instead of one generic JSON grammar.** Strings, integers, and floats each
  have their own continuation-validity function rather than a single shared "is this valid JSON"
  check, since each type has different edge cases (quote escaping and trailing backslashes for
  strings, sign and single-decimal-point handling for numbers).
- **Unknown-function fallback.** A synthetic `Unknown` function (loaded from `Unknown.json`) is
  always added to the candidate list, so an out-of-scope or ambiguous prompt has a valid target
  instead of forcing the decoder to pick the closest wrong function.
- **Pydantic models for every I/O boundary.** `FunctionEntry`, `Prompt`, and
  `FunctionCallResult` validate the function definitions, the input prompts, and the final output
  respectively, so malformed input files fail fast with a clear error instead of crashing deep
  inside generation.

## Performance Analysis

- **Validity**: 100% of outputs are syntactically valid, schema-compliant JSON by construction —
  this is enforced by the decoder, not measured empirically, since invalid tokens are never
  reachable.
- **Accuracy**: function selection is reliable once a prompt clearly maps to one function; the
  main remaining source of error is parameter *value* fidelity on free-form string fields (e.g.
  the model occasionally extending a copied substring past its correct boundary), which the
  repetition guard and numeric-literal grounding are specifically there to reduce.
- **Speed**: since every token is scored with a single forward pass and picked greedily (no
  beam search, no retries), a full test file processes well within the 5-minute target on
  standard hardware.

## Challenges Faced

- **Premature/late string termination.** Early versions of the string-value generator had no
  reliable signal for *when* a value was finished, which let the model wander past the correct
  substring into the next field's text, or loop indefinitely repeating the same characters. This
  was fixed with the repetition-block guard and a hard `MAX_LENGTH` cap per field.
- **Prefix-collision in function-name selection.** Because function names share prefixes (e.g.
  `fn_execute`, `fn_execute_sql_query`), naive greedy decoding could commit to the wrong branch
  after only a couple of tokens. `is_name_token_allowed` keeps every partial name that is still a
  valid prefix of *some* function alive until the closing quote, rather than resolving too early.
- **Numeric field boundaries.** Distinguishing "the number is finished" from "the number
  continues" is ambiguous from grammar alone (`"18` is a valid prefix of `180` and of `18`).
  Grounding candidate values in the literals actually present in the prompt resolves this
  deterministically instead of guessing from logits alone.

## Testing Strategy

- Manual testing against `data/input/function_calling_tests.json`, covering every function in
  `functions_definition.json` and multiple prompt phrasings per function.
- Targeted edge cases: multi-parameter functions (`fn_substitute_string_with_regex`), string
  values containing punctuation/quotes, multi-digit and decimal numbers, and prompts with no
  clear matching function (to exercise the `Unknown` fallback).
- `make lint` (flake8 + mypy) run on every change to catch type and style regressions before
  runtime testing.
- `make test` runs the provided `moulinette` grading harness against the generated
  `data/output/function_calling_results.json` for automated scoring.

failure cases observed in test output — including a prefix-collision bug in function-name
selection, an unbounded string-generation loop causing values to run past their correct
boundary, and a value-hallucination case where the model appended an unrequested suffix to a
copied value. In each case, the assistant was given the actual failing test output and asked to
diagnose the root cause and propose a fix in the existing decoding loop; all proposed fixes were
reviewed, adapted, and integrated manually rather than pasted in directly. AI was not used to
design the overall architecture or write the constrained-decoding approach from scratch.
